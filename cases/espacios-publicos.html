Gestión de Espacios Públicos

Una herramienta interna nacida de un problema operativo concreto: información repartida entre planillas, papel, llamados y seguimiento informal.

Process AnalysisTypeScriptPostgreSQLReactData Modeling
Contexto

El trabajo existía, pero no su trazabilidad.

El área gestiona espacios públicos, pedidos de mantenimiento, intervenciones, agentes y cuadrillas, expedientes, trámites y forestación. Gran parte del seguimiento dependía de registros separados y conocimiento informal.

  • Pedidos que vivían en distintos canales.
  • Dificultad para reconstruir estado e historial.
  • Datos de forestación heredados desde planillas.
  • Reportes que requerían trabajo manual.
  • Usuarios administrativos y operativos con necesidades diferentes.
Solución

Modelar el dominio antes de automatizarlo.

La aplicación centraliza espacios, pedidos, intervenciones, cuadrillas, expedientes, trámites administrativos y reclamos de arbolado. El objetivo no es reemplazar todos los sistemas municipales, sino estructurar el flujo cotidiano del área.

Espacio público
   ↓
Pedido de mantenimiento
   ↓
Asignación / estado
   ↓
Intervención
   ↓
Historial y datos para gestión
Arquitectura

Full-stack modular, orientado al dominio.

Backend Express + TypeScript organizado por módulos y capas `controller → service → repository`, validación Zod y acceso directo a PostgreSQL con `pg`. Frontend React + Vite + TypeScript organizado por feature.

El dominio utiliza términos en español para evitar una capa innecesaria de traducción entre la operación y el código.

UX

Una herramienta para personal no técnico.

  • Estados escritos con palabras completas.
  • Filtros explícitos y persistentes.
  • Formularios en modal para flujos repetitivos.
  • Exportación CSV para convivir con planillas cuando hace falta.
  • Roles y módulos diferenciados según función.
CriterioUn sistema interno que requiere demasiada capacitación crea una nueva fricción en lugar de resolver la anterior.
Mi rol

Relevamiento, modelado e implementación full-stack.

Relevé procesos del área, traduje necesidades operativas y administrativas a módulos, definí modelo de datos, contrato API y arquitectura, implementé backend/frontend e importación de datos heredados y documenté decisiones técnicas y funcionales.

Qué demuestra

Del relevamiento operativo al modelo de datos.

  • Análisis de procesos antes de escribir código.
  • Transformación de necesidades administrativas y operativas en módulos.
  • Diseño de datos, estados e historial.
  • Arquitectura full-stack mantenible.
  • Integración de datos heredados.
  • Decisiones técnicas y funcionales documentadas.
